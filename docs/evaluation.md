# Проверка подсистемы

Документ фиксирует границы прототипа и сценарии, которые удобно показывать на защите.

## Что уже умеет система

- Выделяет сущности из описания предметной области на русском и английском языках.
- Выделяет атрибуты через конструкции `имеет`, `есть`, `has`, а также часть перечислений после `содержит`.
- Определяет связи через семантические шаблоны: принадлежность, состав, действие пользователя, связь объектов.
- Учитывает кратность `one-to-many`, `many-to-one`, `many-to-many`, если она задана явно или выводится из глагола.
- Позволяет вручную исправить сущности, атрибуты, типы и связи перед генерацией SQL.
- Генерирует SQL DDL, JSON модели и Mermaid ER-диаграмму.

## Рекомендуемый стиль входного текста

Лучше всего работают короткие предложения, где одна мысль описывает одну сущность или одну связь:

```text
Клиент имеет имя email телефон.
Заказ имеет номер дату сумму.
Товар имеет название цену.
Клиент оформляет заказы.
Заказ содержит товары.
```

Допустимы более естественные формулировки:

```text
У клиента есть имя и телефон.
Один клиент может иметь несколько заказов.
В системе хранятся клиенты, заказы и товары.
База данных интернет магазина. У нас есть товары которые имеют цену скидку количество на складе. Пользователи у которых есть номер телефона почта дата последней покупки. История заказов которая связана с пользователями.
```

Нежелательно смешивать много фактов в одном длинном предложении. Для правил без LLM это резко снижает точность.

## Тестовые сценарии

### Интернет-магазин

```text
Клиент имеет имя email телефон. Заказ имеет номер дату сумму. Товар имеет название цену. Клиент оформляет заказы. Заказ содержит товары.
```

Ожидаемо:

- сущности: `Клиент`, `Заказ`, `Товар`;
- атрибуты клиента: `имя`, `email`, `телефон`;
- атрибуты заказа: `номер`, `дата`, `сумма`;
- связи: клиент -> заказ, заказ -> товар.

### Библиотека

```text
Читатель имеет имя email телефон. Книга имеет название автора год. Выдача имеет дату выдачи и дату возврата. Читатель имеет несколько выдач. Выдача связана с книгой.
```

Ожидаемо:

- сущности: `Читатель`, `Книга`, `Выдача`;
- связь читатель -> выдача с кратностью один-ко-многим;
- связь выдача -> книга.

### Учебный процесс

```text
Студент имеет имя email группу. Преподаватель имеет имя email должность. Курс имеет название код. Студент записывается на курсы. Преподаватель ведет курсы.
```

Ожидаемо:

- сущности: `Студент`, `Преподаватель`, `Курс`;
- связи студент -> курс и преподаватель -> курс;
- при необходимости кратность можно уточнить вручную в редакторе.

## Ограничения

- Это не генеративный ИИ, поэтому система не понимает произвольный диалог как человек.
- Алгоритм основан на NLP-токенизации, лемматизации, словарях предметных признаков, dependency parsing и rule-based scoring.
- Если spaCy-сервис недоступен, Go-сервис использует локальный fallback. Результат остается рабочим, но морфология и dependency-связи слабее.
- Спорные случаи специально выведены в ручной редактор: пользователь подтверждает структуру до генерации DDL.

## Критерии качества для защиты

- Корректно найдены ключевые сущности.
- Атрибуты не превращаются в отдельные таблицы без необходимости.
- Связи и внешние ключи соответствуют смыслу предметной области.
- Система объясняет, каким правилом найден каждый кандидат.
- После ручной корректировки SQL и ER-представление пересчитываются без повторного анализа текста.
